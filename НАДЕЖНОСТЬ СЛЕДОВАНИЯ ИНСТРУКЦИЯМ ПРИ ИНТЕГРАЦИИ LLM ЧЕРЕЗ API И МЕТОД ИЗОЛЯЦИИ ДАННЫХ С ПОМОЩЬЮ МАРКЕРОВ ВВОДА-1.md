**INSTRUCTION-FOLLOWING RELIABILITY IN LLM API INTEGRATION A DATA**


**ISOLATION APPROACH USING INPUT BOUNDARY MARKERS**

_**Аннотация.**_ В статье рассматривается проблема нестабильного следования
инструкциям при интеграции больших языковых моделей (LLM) через программные
интерфейсы (API) в производственных системах. Описываются явления утечки промпта
(Prompt Leakage), загрязнения контекста (Context Contamination) и перезаписи инструкций
(Instruction Overwriting), приводящие к нарушению логики перевода и обработки текстов.
Проводится сравнительный анализ существующих методов повышения надежности в режиме
JSON-вывода, настройки параметра temperature и использования XML-подобных тегов.
Предлагается авторский метод изоляции пользовательских данных посредством жестких
граничных маркеров <<<INPUT_TEXT>>> / <<<END_INPUT_TEXT>>> в системном
промпте. Метод апробирован на реальной задаче автоматизированного перевода офисных
документов (Excel, DOCX, DXF, DWG) с использованием локально развернутой LLM.
Экспериментально показано, что применение маркеров снижает частоту ошибок контекстного

смешения до нуля в стандартных условиях использования.

_**Abstract.**_ This paper addresses the problem of unreliable instruction-following in Large
Language Model (LLM) API integrations within production environments. We describe the
phenomena of Prompt Leakage, Context Contamination, and Instruction Overwriting, which lead to
failures in automated text processing pipelines. A comparative analysis of existing mitigation
approaches is conducted, including JSON output mode, temperature tuning, and XML-like delimiters.
We propose a method of user-data isolation using hard boundary markers <<<INPUT_TEXT>>> /
<<<END_INPUT_TEXT>>> embedded in the system prompt. The method is validated on a realworld automated document translation task (Excel, DOCX) using a locally deployed LLM.
Experiments demonstrate that boundary markers eliminate context-mixing errors under standard
operating conditions.


_**Keywords:**_ _large language models, prompt engineering, LLM API, prompt leakage, context_
_isolation, input markers, instruction reliability, automated translation, system prompt, Context_
_Contamination_


**Введение**


Интеграция больших языковых моделей (LLM) в производственные информационные
системы посредством API (Application Programming Interface) становится стандартной
практикой в современной инженерии программного обеспечения. Такие модели, как GPT-5




---

(OpenAI), Claude (Anthropic), Gemini (Google), а также открытые альтернативы (LLaMA,
Gemma), предоставляют высокоуровневый интерфейс для решения задач обработки
естественного языка, такие как перевод, классификация, резюмирования, извлечения
информации [1].

Вместе с тем внедрение LLM в реальные рабочие процессы выявляет фундаментальную
проблему, модели не всегда строго следуют системным инструкциям при наличии
пользовательского ввода. Данная проблема, описываемая в литературе как Prompt Leakage,
Instruction Overwriting или Context Contamination [2], проявляется в том, что модель

«перемешивает» содержимое системного промпта и пользовательских данных, игнорируя
ограничения или обрабатывая инструкцию как часть входных данных. В задаче машинного
перевода это приводит к переводу самой инструкции вместо переводимого текста, или к
включению в вывод служебных фраз-шаблонов.

Целью настоящей работы является анализ механизма возникновения контекстного
смешения, систематическое сравнение известных методов противодействия, а также описание
и обоснование авторского метода изоляции данных с помощью жестких маркеров ввода,
реализованного в производственной системе перевода офисных документов.


**Теория**


Современные LLM обрабатывают входную последовательность как единый
токенизированный контекст. Согласно архитектуре трансформера, механизм внимания
(attention) не проводит формальной границы между системным промптом и пользовательским
вводом, оба представлены токенами в одном контекстном окне [3]. Граница между ними
обозначается лишь специальными токенами-разделителями, специфичными для каждой
модели и формата ее обучения (например, <|system|>, <|user|> в формате ChatML).

При высоких значениях параметра temperature или при длинном пользовательском
вводе, содержащем языковые конструкции, семантически близкие к инструкции, модель с
ненулевой вероятностью «продолжает» инструкционный контекст вместо пользовательского

[4]. Этот эффект усиливается при использовании моделей с режимом «длинного мышления»
(extended thinking, chain-of-thought), поскольку внутренние рассуждения модели смешиваются

с конечным выводом.

Как видно из таблицы, каждый из существующих методов имеет принципиальные
ограничения. JSON mode не устраняет семантического смешения на уровне обработки текста.
Снижение temperature повышает детерминированность, но не изолирует контексты. XML-теги
зависят от особенностей обучения конкретной модели и могут воспроизводиться в выводе.


**Результаты**


Метод жестких граничных маркеров. Предлагаемый метод основан на введении в
системный промпт явных граничных токенов, формирующих семантически уникальный
контейнер для пользовательских данных. В качестве маркеров используются
последовательности <<<INPUT_TEXT>>> и <<<END_INPUT_TEXT>>>, которые не
встречаются в естественных языковых корпусах и обладают высокой токенной
специфичностью [5].

Принцип работы метода состоит в следующем. В системный промпт включается явная
инструкция, определяющая семантику маркеров, модель должна обрабатывать

исключительно содержимое между открывающим и закрывающим маркерами, игнорируя
маркеры в выводе. В пользовательском вводе передаваемые данные оборачиваются теми же
маркерами. Таким образом, граница «инструкция – данные» становится явной на уровне
токенизации, а не неявной через форматный разделитель роли.

Реализация метода продемонстрирована на рис. 1.


Рис. 1. Реализация метода жестких ограничений маркеров


Данная реализация обеспечивает несколько взаимосвязанных свойств надежности. Вопервых, модель явно информируется о том, что маркеры не являются частью переводимого
текста и не должны присутствовать в выводе. Во-вторых, секция OUTPUT RULES закрепляет
принцип вывода «только перевод, без добавлений», что совместно с маркерами формирует
двухуровневую защиту от шаблонных фраз-заготовок (boilerplate). В-третьих, метод
_clean_model_output выполняет постобработку с явным удалением маркеров из вывода как

дополнительную страховку.

Система была протестирована на корпусе технических и юридических документов
общим объемом более 10 гб в форматах DOCX, XLSX, DXF и DWG. В качестве базовой
модели использовалась translategemma:12b, развернутая локально на корпоративном сервере с
ollama. Тестирование проводилось в трех режимах: (а) без маркеров, с temperature=0.7; (б) без
маркеров, с temperature=0.1; (в) с маркерами <<<INPUT_TEXT>>>, с temperature=0.1.

Основным измеряемым показателем являлась частота ошибок контекстного смешения,
когда модель включала в вывод фрагменты системного промпта, маркеры или шаблонные
вводные фразы («Вот перевод:», «Sure, here is:» и т.п.). В режиме (а) частота таких ошибок
составила 3,2% от числа запросов. В режиме (б) - 1,4%. В режиме (в) - 0,0% за все время
тестирования, что подтверждает практическую эффективность предложенного метода.

**Выводы и заключение**


Проведенное исследование показывает, что явление контекстного смешения является
фундаментальной проблемой при интеграции LLM через API и зависит от архитектурных
особенностей трансформера и от параметров. Существующие методы, такие как JSON mode,
настройка temperature, XML-теги, эффективны лишь частично и не дают гарантий.

Предлагаемый метод жестких граничных маркеров <<<INPUT_TEXT>>> /
<<<END_INPUT_TEXT>>> обладает следующими преимуществами перед аналогами: не
зависит от поддержки специальных режимов конкретного API; маркеры не встречаются в
обучающих данных; около 6 дополнительных токенов на запрос; декларативная инструкция и
постобработка вывода.

Практические тесты на задачах автоматизированного перевода документов
подтвердили нулевую частоту ошибок контекстного смешения при использовании маркеров.
